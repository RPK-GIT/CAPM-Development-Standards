# CAP-INT — Integration & remote services

Part of the [Layer 2 rule catalog](README.md). Rules follow the [rule template](../../templates/rule-template.md) and the catalog invariants. Candidate dispositions: [references/candidate-dispositions.md](../../references/candidate-dispositions.md). Related ORG gaps: G-27, G-28, G-29 in [research-gaps.md](../../references/research-gaps.md).

**Rules:** 7 active (0 Critical, 3 High, 4 Medium). All SAP references verified against official CAP documentation on **2026-08-11**.

Scope boundaries — this category governs consumption of **external/remote systems**. It deliberately does not restate: asynchronous eventing and brokers ([CAP-EVT](events-messaging.md)), credentials/secrets incl. destination credentials ([CAP-SEC-017](security.md)), remote calls inside transactions and no-distributed-atomicity ([CAP-TXN-005](transactions.md)), or service-to-service auth ([CAP-SEC-009](security.md)). Guarantee discipline per Batch 3 applies: no resilience or atomicity behavior is claimed beyond what SAP documents.

**Applicability precondition:** these rules apply to projects consuming remote/external services. Projects without remote consumption are NOT APPLICABLE throughout — state the evidence (no `srv/external/`, no remote-service configuration).

## CAP-INT-001 — Import external APIs with `cds import`; OData V4 between CAP services

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-001 |
| **Title** | Import external APIs with `cds import`; OData V4 between CAP services |
| **Category** | Integration & remote services |
| **Severity** | High |
| **Authority** | SAP-REQ (documented copy-problems; "Always use OData V4 (`odata`) when calling another CAP service"); EDMX exchange format is SAP-REC ("we recommend") |
| **Applicability** | All projects consuming remote service APIs |
| **Runtime** | Both |
| **CAP version** | All currently supported versions (`cds import` accepts EDMX OData V2/V4, OpenAPI, AsyncAPI) |
| **Status** | Active |
| **Related rules** | CAP-INT-002, CAP-INT-003, CAP-SRV-005 (V4-first for own APIs) |
| **Last verified** | 2026-08-11 |

### Rule statement
External service definitions MUST be brought into the project with `cds import` (EDMX for OData V2/V4, OpenAPI, AsyncAPI) into `srv/external/` — never by copying CDS files from another application, whose documented problems are: the effective API depends on the protocol, includes can't be resolved, and "CAP creates unneeded database tables and views for all entities in the file". When one CAP service consumes another CAP service, OData V4 MUST be used (SAP: "Always use OData V4 (`odata`) when calling another CAP service"), with EDMX as the recommended exchange format.

### Rationale
`cds import` produces definitions marked as external — no persistence artifacts, protocol-correct shapes, resolvable standalone. Copied CDS files silently generate **database tables for remote entities**: the application appears to work while writing to a local shadow of the remote system — a data-integrity trap, not just hygiene. The V4 requirement keeps CAP-to-CAP contracts on the current protocol line (mirroring CAP-SRV-005 on the provider side). **High:** shadow persistence of remote data and protocol-broken API shapes materially corrupt integration correctness.

### Evidence expected in code
`srv/external/*.cds`/`.csn` generated by `cds import` (registered under `cds.requires` with `model` references); no hand-copied foreign CDS models; CAP-to-CAP consumption configured with OData V4.

### Detection guidance
1. Inspect `srv/external/` and `package.json` `cds.requires`: external services declared with `kind: odata`/`odata-v2`/... and `model` pointing at imported definitions → expected shape.
2. Look for copied models: external-system entities defined in regular `db/`/`srv/` model files (namespaces of foreign products, entities duplicating a remote API) → FAIL with file:line.
3. Check compiled artifacts/db folder: database tables generated for remote entities (remote-namespace `.hdbtable`, CSV data for external entities outside mocking folders) → FAIL (shadow persistence).
4. For CAP-to-CAP consumption: `kind: odata-v2` against a CAP provider → FAIL (documented "always V4").
5. Report per external API.

### Good example
```jsonc
// package.json — imported API, no local persistence
{ "cds": { "requires": { "API_BUSINESS_PARTNER": {
    "kind": "odata-v2", "model": "srv/external/API_BUSINESS_PARTNER"
} } } }
```

### Bad example
```text
db/external-bp.cds containing a hand-copied A_BusinessPartner entity —
cds deploy now creates a local A_BUSINESSPARTNER table; handlers read
stale local rows believing they query S/4.
```

### Exception guidance
CAP-to-CAP APIs shared as npm packages (documented Calesi path) are imported via the package, not `cds import` — equally compliant. Consuming a non-CAP legacy system that only offers V2 is the documented use of `kind: odata-v2` (the always-V4 requirement binds CAP-to-CAP calls).

### SAP reference
- https://cap.cloud.sap/docs/guides/services/consuming-services (`cds import`; the three documented copy-problems; "Always use OData V4 when calling another CAP service"; EDMX recommendation)

## CAP-INT-002 — Consume remote systems through CAP remote services and destinations

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-002 |
| **Title** | Consume remote systems through CAP remote services and destinations |
| **Category** | Integration & remote services |
| **Severity** | High |
| **Authority** | SAP-REC (uniform consumption is the documented model; REQ elements: Java Remote Services "need to be configured explicitly"; on-premise access needs Connectivity service + Cloud Connector) |
| **Applicability** | All remote-system consumption where CAP supports the protocol |
| **Runtime** | Both (Java: Remote Services never auto-created — explicit configuration; destinations via Cloud SDK `DestinationAccessor`) |
| **CAP version** | All currently supported versions |
| **Status** | Active |
| **Related rules** | CAP-ARCH-002/-005 (hand-rolled clients are framework bypasses), CAP-SEC-017 (no credentials in config), CAP-EVT-001 (async counterpart), CAP-INT-007; destination governance is ORG gap G-28 |
| **Last verified** | 2026-08-11 |

### Rule statement
Remote systems whose protocols CAP supports MUST be consumed through CAP's remote-service mechanism — imported definition (CAP-INT-001), `cds.requires` configuration, `cds.connect.to(...)` / configured Java Remote Services, queried with CQN as if local — with connectivity resolved through **destinations** (BTP Destination service; application-defined destinations only per CAP-SEC-017's credential rules; on-premise systems additionally require the Connectivity service and Cloud Connector). Hand-rolled HTTP clients for such systems MUST NOT be used without a documented CAP-ARCH-002 exception. Java note: Remote Services are "never created automatically" — the explicit configuration *is* part of compliance.

### Rationale
The remote-service abstraction is where CAP centralizes what hand-rolled clients each reimplement: destination resolution (with tenant awareness — the Destination service looks up "from the subaccount of the current tenant"), authentication/token handling, query translation, mocking (CAP-INT-004), and uniform consumption ("Remote CAP services can be consumed using the same high-level, uniform APIs as for local services"). A bespoke `fetch`/`RestTemplate` client silently loses tenant-correct destination lookup and token exchange — security- and tenancy-adjacent failures, not just style. **High:** hand-rolled clients routinely mishandle exactly the auth/tenant concerns the abstraction exists for.

### Evidence expected in code
`cds.requires` entries with destination references; `cds.connect.to`/`@Autowired`-injected Remote Services in handlers; no ad-hoc HTTP clients targeting systems CAP could consume natively.

### Detection guidance
1. Inventory remote consumption: `cds.requires` externals (Node), Remote Service configs (Java `application.yaml` `cds.remote.services`), destination names used.
2. Search for hand-rolled clients: `fetch(`/`axios`/`node-fetch` (Node), `RestTemplate`/`WebClient`/`HttpClient` (Java) targeting business systems in `srv/**` → per site: protocol supported by CAP (OData V2/V4, documented import types)? → yes without documented exception → FAIL with file:line.
3. Verify destination usage: connectivity via destination names, not hardcoded URLs (URLs inline in code/config for remote business systems → FAIL; cross-report CAP-SEC-017 if credentials ride along).
4. On-premise targets: verify Connectivity service binding + Cloud Connector documented in deployment artifacts → missing → FAIL.
5. Java: each consumed remote API has its explicit Remote Service configuration → missing (worked around via direct HTTP) → FAIL.
6. Report per remote system.

### Good example
```js
// Node.js — uniform consumption via imported definition + destination
const bupa = await cds.connect.to('API_BUSINESS_PARTNER');
const partners = await bupa.run(SELECT.from('A_BusinessPartner').limit(100));
```
```jsonc
{ "cds": { "requires": { "API_BUSINESS_PARTNER": {
    "kind": "odata-v2", "model": "srv/external/API_BUSINESS_PARTNER",
    "[production]": { "credentials": { "destination": "S4HANA" } }
} } } }
```

### Bad example
```js
// hand-rolled client: hardcoded URL, manual token plumbing, no tenant-aware
// destination resolution, unmockable in the inner loop
const res = await fetch('https://s4.example.com/sap/opu/odata/sap/API_BUSINESS_PARTNER/A_BusinessPartner', {
  headers: { Authorization: 'Bearer ' + await fetchTokenSomehow() }
});
```

### Exception guidance
Protocols CAP doesn't support (proprietary APIs, non-importable formats) legitimately need a dedicated client — isolated, documented per CAP-ARCH-002/-007, resolving connectivity through destinations where possible, and still subject to CAP-INT-007. One-off platform/admin API calls (not business-data integration) are out of scope.

### SAP reference
- https://cap.cloud.sap/docs/guides/services/consuming-services (consumption model; destinations; on-premise Connectivity service + Cloud Connector)
- https://cap.cloud.sap/docs/guides/integration/calesi (remote services proxied by CAP services; uniform APIs; automatic mocking)
- https://cap.cloud.sap/docs/java/cqn-services/remote-services (explicit configuration required; `DestinationAccessor`; tenant-aware destination lookup)

## CAP-INT-003 — Access remote entities through consumption views

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-003 |
| **Title** | Access remote entities through consumption views |
| **Category** | Integration & remote services |
| **Severity** | Medium |
| **Authority** | SAP-REC ("always prefer doing so via consumption views"; formally optional — "good practice to always define consumption views on top of imported APIs") |
| **Applicability** | All consumption of imported remote APIs |
| **Runtime** | Both |
| **CAP version** | All currently supported versions |
| **Status** | Active |
| **Related rules** | CAP-INT-001, CAP-SRV-001 (the same facade principle, remote edition), CAP-INT-005 |
| **Last verified** | 2026-08-11 |

### Rule statement
Imported remote APIs SHOULD be accessed through consumption views — CDS projections in the application's own namespace mapping remote definitions to the domain (field selection, renaming, domain vocabulary) — rather than using raw imported entities throughout handlers or re-exposing them 1:1. SAP: "Even when accessing remote services directly, always prefer doing so via consumption views. They map the remote definitions to your domain, and allow CAP to automatically translate queries accordingly."

### Rationale
Consumption views are the anti-corruption layer CAP gives you for free: the remote API's shape (hundreds of `A_BusinessPartner` fields, foreign naming) stays at the boundary; the application codes against its own vocabulary; CAP translates queries automatically; a remote API version change touches one view, not every handler. Raw remote entities spread through the codebase couple the domain to a foreign contract. **Medium (downgraded from candidate High):** a maintainability/coupling concern — nothing fails until the remote contract moves; re-exposure breadth concerns escalate through CAP-SRV-001.

### Implementation guidance
- Define one projection per use case on the imported entity, selecting only needed fields and renaming into domain vocabulary; consume *that* in handlers.
- Re-exposing remote data in own services goes through the same views (then CAP-SRV-001 applies to the exposure shape).

### Evidence expected in code
Projections on `srv/external/*` entities in the project's namespace; handlers querying the views (or narrowly the imported entity at the boundary module), not raw remote entities scattered across the codebase.

### Detection guidance
1. List imported entities (from `srv/external/`) and search `srv/**` for direct references to them.
2. Consumption views defined (projections on external entities) and used by handlers → PASS.
3. Raw imported entities referenced across multiple handlers/services with no view layer → FAIL (Medium) with the spread (count + representative file:line).
4. Own service definitions exposing imported entities 1:1 → FAIL here and cross-report CAP-SRV-001.
5. Single-site boundary usage inside one integration module → PASS with note (the module *is* the boundary).

### Good example
```cds
// srv/external-mashup.cds — remote definition mapped to domain vocabulary
using { API_BUSINESS_PARTNER as external } from './external/API_BUSINESS_PARTNER';
entity Suppliers as projection on external.A_BusinessPartner {
  key BusinessPartner as ID, BusinessPartnerFullName as name
}
```

### Bad example
```js
// raw remote entity + foreign field names spread through business logic
const bp = await bupa.run(SELECT.from('API_BUSINESS_PARTNER.A_BusinessPartner')
  .columns('BusinessPartner','BusinessPartnerFullName','BusinessPartnerCategory'));
order.supplierName = bp[0].BusinessPartnerFullName;   // repeated in 14 handlers
```

### Exception guidance
Thin pass-through integrations (single endpoint forwarding) may reasonably work on the imported entity directly at one boundary site — record the choice. Generated integration code from SAP tooling follows its own conventions.

### SAP reference
- https://cap.cloud.sap/docs/guides/integration/calesi ("always prefer doing so via consumption views"; automatic query translation)

## CAP-INT-004 — Mock remote dependencies for local development and tests

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-004 |
| **Title** | Mock remote dependencies for local development and tests |
| **Category** | Integration & remote services |
| **Severity** | Medium |
| **Authority** | SAP-REC (documented mocking mechanisms; Java `--with-mocks` is REQ-phrased: "make sure to add") |
| **Applicability** | Projects consuming remote services, in their development/test setup |
| **Runtime** | Both (mechanics differ: Node in-process/`cds mock`; Java requires `cds deploy --with-mocks` for the schema) |
| **CAP version** | All currently supported versions |
| **Status** | Active |
| **Related rules** | CAP-INT-002, CAP-EVT-007 (the messaging sibling), CAP-SEC-017 (no cloud credentials locally); test-depth requirements belong to the future CAP-TEST category |
| **Last verified** | 2026-08-11 |

### Rule statement
Every consumed remote service MUST be mockable and mocked in local development and default tests: CAP mocks imported services automatically in the inner loop (`cds watch` — "The service is automatically mocked"; separate-process mocking via `cds mock <API>`), with sample data as CSV in `srv/external/data`; CAP Java projects MUST add `--with-mocks` to the `cds deploy` command generating the test schema (SAP: "make sure to add"). Local development MUST NOT require live connectivity to external systems.

### Rationale
Mocked remotes are what keep CAP's inner loop ("airplane mode", CAP-ARCH-005) intact for integrated applications: development and CI run without VPNs, credentials (CAP-SEC-017), or a test tenant in the remote system — and failure-path tests become possible at all. Unmockable integrations force shared-system coupling of every developer and pipeline run. **Medium:** development-infrastructure quality with direct CI-stability consequences.

### Evidence expected in code
`srv/external/data/*.csv` sample data; dev profile without live destinations; Java `srv/pom.xml` cds deploy invocation containing `--with-mocks`; CI running integration-relevant tests without external connectivity.

### Detection guidance
1. For each imported API (CAP-INT-001 inventory), check mock data exists (`srv/external/data/<API>-<Entity>.csv`) → missing where tests touch the API → FAIL element.
2. Check dev/default profiles: external services must not require live `credentials`/destinations to start (`cds watch` runs standalone) → live-only config → FAIL.
3. Java: inspect `srv/pom.xml` for the `cds deploy` schema generation — `--with-mocks` present → PASS; absent while remote entities are queried in tests → FAIL (documented requirement).
4. Verify CI needs no external connectivity for the default test suite (pipeline config; cross-note future CAP-TEST for coverage depth).
5. NOT APPLICABLE without remote consumption.

### Good example
```text
srv/external/data/API_BUSINESS_PARTNER-A_BusinessPartner.csv   ← mock data
cds watch    → "mocking API_BUSINESS_PARTNER" in the log; no VPN, no creds
srv/pom.xml  → cds deploy … --with-mocks   (Java schema incl. mocked entities)
```

### Bad example
```text
Local startup fails without corporate VPN because the dev profile points
at the live S/4 destination; CI skips all integration tests "because
credentials"; no CSV mock data anywhere.
```

### Exception guidance
Remote features genuinely untestable via mocks (SSO flows, remote-side validations) are hybrid-test material (`cds bind --exec`, per CAP-DB-002's pattern) — as an *addition* to mocks, not a replacement. Contract-test setups with recorded responses are a compliant alternative when documented.

### SAP reference
- https://cap.cloud.sap/docs/guides/services/consuming-services (automatic in-process mocking; `cds mock <API>`; CSV in `srv/external/data`; Java `--with-mocks`)
- https://cap.cloud.sap/docs/guides/integration/calesi (mocking out of the box for inner-loop development)

## CAP-INT-005 — Control cross local/remote expands and mashups

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-005 |
| **Title** | Control cross local/remote expands and mashups |
| **Category** | Integration & remote services |
| **Severity** | High |
| **Authority** | SAP-REC (documented warning: "can cause stability and performance issues"; "Consider to reject expands if it's requested on a list of items") |
| **Applicability** | Services combining local and remote entities (mashups, cross-source associations) |
| **Runtime** | Both |
| **CAP version** | All currently supported versions |
| **Status** | Active |
| **Related rules** | CAP-INT-003, CAP-SEC-014 (request-amplification sibling), CAP-INT-007, CAP-TXN-005 |
| **Last verified** | 2026-08-11 |

### Rule statement
Navigations and `$expand` spanning local and remote entities MUST be implemented deliberately (custom handlers are required — CAP does not resolve them generically) and MUST be bounded: SAP warns that "Expands across local and remote can cause stability and performance issues" (collected ID lists "may exceed the limits of a URL string"), advising to "Consider to reject expands if it's requested on a list of items". Mashup handlers MUST cap or reject list-level cross-source expands and MUST NOT fan out one remote request per result row.

### Rationale
A cross-source expand on a list turns one user request into N remote calls or one gigantic `$filter` URL — the documented stability risk. Unbounded mashups couple the application's availability to the remote system's latency for every list view (and amplify into CAP-SEC-014's DoS territory when client-controlled). **High:** unbounded cross-remote expansion is a production-stability defect on the normal path, not an edge case, once list sizes grow.

### Implementation guidance
- Allow cross-source expand on single-instance reads; reject or paginate it on collections (SAP's documented advice).
- Batch remote lookups (one remote query for all needed IDs, bounded chunk size) instead of per-row calls; consider replication/federation when remote data is needed for filtering/sorting at scale (criteria = ORG gap G-29).

### Evidence expected in code
Mashup handlers with explicit expand policy (reject on collections / bounded batching); no per-row remote calls in list handlers.

### Detection guidance
1. Identify cross-source associations/mashups: models associating local and `srv/external/` entities; handlers combining both sources.
2. Inspect the list-read path: remote call inside a loop over result rows → FAIL (N+1 remote fan-out) with file:line.
3. Check expand policy: `$expand` on cross-source associations for collections either rejected (documented advice) or bounded (chunked ID batching with a size cap) → neither → FAIL.
4. Verify single-instance expands assemble via one remote query.
5. Cross-report client-controllable amplification to CAP-SEC-014.
6. NOT APPLICABLE without cross-source mashups.

### Good example
```js
srv.on('READ', 'Orders', async (req, next) => {
  const orders = await next();
  if (!req.query.SELECT.columns?.some(c => c.expand && c.ref[0] === 'supplier')) return orders;
  if (orders.length > 100) return req.reject(400, 'EXPAND_LIMIT');   // documented advice
  const ids = [...new Set(orders.map(o => o.supplier_ID))];
  const suppliers = await bupa.run(SELECT.from(Suppliers).where({ ID: { in: ids } }));
  return mergeSuppliers(orders, suppliers);                          // one bounded remote call
});
```

### Bad example
```js
srv.after('READ', 'Orders', async orders => {
  for (const o of orders)                                   // N+1 remote fan-out:
    o.supplier = await bupa.run(SELECT.one.from(Suppliers, o.supplier_ID));
});                                                          // 5,000 rows = 5,000 remote calls
```

### Exception guidance
Small, bounded collections (code-list-sized) may expand cross-source without chunking — record the bound assumption. Replicated/federated data (remote data persisted locally per a documented decision, G-29) removes the remote hop and this rule's applicability for that path.

### SAP reference
- https://cap.cloud.sap/docs/guides/services/consuming-services (expand warning; URL-length mechanism; "Consider to reject expands… on a list of items")

## CAP-INT-006 — Decide destination retrieval strategy deliberately in multitenant apps

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-006 |
| **Title** | Decide destination retrieval strategy deliberately in multitenant apps |
| **Category** | Integration & remote services |
| **Severity** | Medium |
| **Authority** | SAP-REC (documented default + documented override) |
| **Applicability** | Multitenant projects consuming remote services via destinations; NOT APPLICABLE for single-tenant apps |
| **Runtime** | Both (Node.js `selectionStrategy: "alwaysProvider"`; Java `retrievalStrategy: "AlwaysProvider"`) |
| **CAP version** | All currently supported versions |
| **Status** | Active |
| **Related rules** | CAP-MT-003 (the isolation stake), CAP-INT-002; destination governance is ORG gap G-28 |
| **Last verified** | 2026-08-11 |

### Rule statement
Multitenant applications MUST make an explicit, recorded decision per consumed destination: subscriber-tenant lookup (the documented default — the destination is read from the tenant of the request's JWT) versus provider-account lookup (`selectionStrategy: "alwaysProvider"` / `retrievalStrategy: "AlwaysProvider"`). The choice MUST match the integration's ownership semantics: tenant-owned systems (each customer's own S/4) → subscriber lookup; provider-owned systems (the SaaS vendor's shared services) → provider strategy.

### Rationale
The wrong strategy is a tenancy defect: provider strategy against tenant-owned systems sends every tenant's requests to the provider's destination (wrong system — and a cross-tenant data-flow hazard adjacent to CAP-MT-003); the default subscriber lookup against a provider-owned system fails per tenant or forces the provider to replicate destinations into every subscriber subaccount. Because the default is silent, an undecided configuration is indistinguishable from a wrong one. **Medium:** configuration-correctness with tenancy stakes; the hard isolation guarantee itself lives in CAP-MT-003.

### Evidence expected in code
Per-destination strategy configuration (or documented reliance on the subscriber default) matching documented ownership of each remote system (integration notes/ADR).

### Detection guidance
1. Confirm multitenancy (CAP-MT profile); else NOT APPLICABLE.
2. List consumed destinations (CAP-INT-002 inventory) and their configured strategy (`selectionStrategy`/`retrievalStrategy` present or default).
3. For each, locate the ownership statement (integration docs/ADR: tenant-owned vs provider-owned) → no record and non-obvious ownership → FAIL (undecided).
4. Mismatch (provider strategy on a tenant-owned system or vice versa) → FAIL with config file:line.
5. Report per destination.

### Good example
```jsonc
// provider-owned shared pricing service — explicitly provider-scoped (ADR-0015)
{ "cds": { "requires": { "PricingService": { "kind": "odata",
    "credentials": { "destination": "PRICING", "selectionStrategy": "alwaysProvider" } } } } }
```

### Bad example
```text
Multitenant app consuming each customer's own S/4 system, configured with
alwaysProvider "because it worked in the dev subaccount" — every tenant's
requests now hit the provider's test S/4.
```

### Exception guidance
Single-tenant deployments and purely provider-internal integrations need no per-destination record beyond the default note. Hybrid ownership (some tenants bring their own system) is a documented design of its own (ADR per CAP-ARCH-007).

### SAP reference
- https://cap.cloud.sap/docs/guides/services/consuming-services (subscriber-tenant default; `alwaysProvider`/`AlwaysProvider` override)
- https://cap.cloud.sap/docs/java/cqn-services/remote-services (tenant-aware destination lookup; `retrievalStrategy`)

## CAP-INT-007 — Design remote calls for failure

| Field | Value |
|---|---|
| **Rule ID** | CAP-INT-007 |
| **Title** | Design remote calls for failure |
| **Category** | Integration & remote services |
| **Severity** | Medium |
| **Authority** | SAP-REC for the duty (SAP documents resilience as needed and names mechanisms — service mesh, Java `ResilienceDecorator`, Node.js community packages — without prescribing one); mechanism choice and thresholds are GEN/ORG (gap G-27). No CAP-framework resilience behavior is claimed: CAP Node.js has "no resilience library provided out of the box", and the Java Remote Services configuration documents no timeout/retry options |
| **Applicability** | All synchronous remote calls in application flows |
| **Runtime** | Both — with runtime-specific documented options: Java may wrap calls with SAP Cloud SDK `ResilienceDecorator.executeSupplier` + `ResilienceConfiguration` (optional fallback); Node.js uses community packages or platform-level means; a service mesh (e.g., Istio) is a documented no-code-change alternative for both |
| **CAP version** | All currently supported versions; Cloud SDK resilience per its own versioning |
| **Status** | Active |
| **Related rules** | CAP-TXN-005 (no atomicity with remote systems — failure design includes partial-failure design), CAP-EVT-002/-003 (queue + idempotency for async decoupling), CAP-INT-005, CAP-SEC-016 (error content in logs); concrete policies are ORG gap G-27 |
| **Last verified** | 2026-08-11 |

### Rule statement
Every synchronous remote call in an application flow MUST have deliberate failure behavior, decided and visible per integration: (1) a bounded wait (timeout at *some* layer — resilience wrapper, HTTP client options, or service mesh — CAP itself provides none); (2) a defined outcome on failure — propagate a meaningful error to the caller (future CAP-ERR mechanics), use a documented fallback, or decouple via the transactional queue where the operation tolerates asynchrony (CAP-EVT-002); (3) retries only where the remote operation is idempotent or made so (CAP-EVT-003 discipline), never blind; (4) remote-write failure semantics designed per CAP-TXN-005 (no distributed atomicity). Where a resilience mechanism is used, it SHOULD be one of SAP's named options (Cloud SDK `ResilienceDecorator` for Java; community packages for Node.js; service mesh for either). Concrete timeout/retry values are ORG policy (G-27).

### Rationale
SAP's consuming-services guide treats resilience as the application's problem and names the mechanism menu — but neither CAP runtime imposes timeouts or retries on remote calls, so the *absence of a decision* means unbounded waits on hung remotes (thread/request exhaustion under load) and accidental duplicate side effects from ad-hoc retries. This rule requires the decision without inventing behavior SAP doesn't provide — the same guarantee discipline as CAP-TXN-005/CAP-EVT-003. **Medium:** design-duty rule; concrete production incidents from violations escalate through the cross-referenced rules and ops monitoring (future CAP-OPS).

### Implementation guidance
- Prefer removing the synchronous dependency: queue the interaction (CAP-EVT-002) when the flow doesn't need the remote answer *now*.
- Java: wrap business-critical remote calls in `ResilienceDecorator.executeSupplier(..., config)` with a `ResilienceConfiguration` (and a fallback where a degraded answer is acceptable).
- Node.js: pick one project-standard mechanism (community resilience package or platform/mesh) and apply it uniformly — per-call improvisation is the anti-pattern.
- Document the per-integration decision (timeout source, retry stance, failure outcome) in the integration notes — one paragraph, reviewable.

### Evidence expected in code
Per-integration failure design visible: resilience wrapper/config, mesh configuration reference, or documented client options; failure-path handling in handlers (error mapping/fallback/queue); no blind retry loops around non-idempotent writes.

### Detection guidance
1. Inventory synchronous remote call sites (CAP-INT-002 inventory; `.run(...)`/`.send(...)` on remote services in request flows).
2. For each integration, locate the bounded-wait mechanism: `ResilienceDecorator` usage (Java), a configured resilience/timeout package (Node), or mesh/platform configuration referenced in deployment artifacts → none anywhere → FAIL (unbounded waits).
3. Inspect failure paths: remote errors swallowed silently (empty catch, `catch { return [] }` masking outages) → FAIL; mapped to meaningful request errors or documented fallback → PASS.
4. Search for retry loops around remote **writes**: idempotency of the remote operation established (idempotency key, remote upsert semantics) → PASS; blind retry of non-idempotent writes → FAIL (cross-report CAP-EVT-003 discipline).
5. Check flows that could be asynchronous but block on remote calls → observation recommending queue decoupling (not FAIL).
6. NOT ASSESSABLE where the bounded wait lives only in un-inspectable platform config — name the needed evidence (mesh/route config export).

### Good example
```java
// Java — documented Cloud SDK mechanism: bounded, with fallback
ResilienceConfiguration config = ResilienceConfiguration.of(SupplierSync.class)
    .timeLimiterConfiguration(TimeLimiterConfiguration.of(Duration.ofSeconds(5)));
List<Suppliers> result = ResilienceDecorator.executeSupplier(
    () -> remote.run(query).listOf(Suppliers.class),
    config,
    e -> cachedSuppliers());   // degraded but defined outcome
```

### Bad example
```js
// unbounded wait + blind retry of a non-idempotent write + swallowed outage
async function chargeCustomer(data) {
  for (let i = 0; i < 10; i++) {
    try { return await billing.send('POST', '/charges', data); }  // duplicate charges on timeout-after-success
    catch (e) { /* retry */ }
  }
  return null;                                                    // outage silently becomes "no charge"
}
```

### Exception guidance
Dev-only tooling calls and one-off admin scripts are out of scope. Integrations fronted by a platform gateway/mesh that demonstrably enforces timeouts satisfy element (1) at that layer — the review then checks the platform configuration reference instead of code.
